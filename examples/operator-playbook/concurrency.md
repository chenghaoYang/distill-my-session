## 跨 session 的四个问题

**1. 一次开几个，怎么照看？**
按日志划分的活跃区间，同时活跃的 session 均值约 1.5 个，人的 prompt 在 session 间切换约每活跃小时 3 次；这些统计不能测出人同时照看了几个 session。同时活跃的 agent 均值为 3.7，峰值为 15 [timeline]。可见的照看方式多数是短句：「如何了」「继续」，有时一分钟内对两个 session 发同一句话 [S28·T14–T18]。

**2. 任务之间的独立是找到的，还是设计出来的？**
是设计出来的。同一个研究项目在一周里有执行、审阅、讲解、清理、补实验几种 session，分工明确 [S32 hindsight]：

- 执行 session 带 agent team 跑实验；
- 审阅 session（常用另一个 harness）读执行 session 的进度，写 review.md，还替操作者写好发给执行 session 的下一条 prompt [S21·T5→S15·T16]；
- 讲解 session 只负责把报告讲给操作者听 [S07·T2]；
- 依赖靠文件切断：goal.md、状态文件、review 文件、调用指南。一个 session 写调用指南并让出服务，另一个 session 36 分钟后按指南开 60 并发 [S61·T13→T18][S65·T4]。

**3. 什么没被审，用什么代替了审阅？**
在 6 个精读 session 的会话记录里，没有操作者读代码、读数据、读报告正文或核数字的痕迹。代替审阅的是：

| 负对照、预注册、A/A 校准 | [S32·T9.14] [S65·T6.16] [S50·T10] |

**4. 是什么让目标活过好几个小时？**
主要是文件：goal.md、实验计划、运营约定、心跳 prompt 本身 [S32·T2][S65·T4][S61·T5][S63·T6]。其次是 compaction summary：它会逐字保留常设规则和用户的选择 [S32·T7.8][S28·T21][S50·T9]。操作者 7 天里只设了 3 次 `/goal`，而且 goal hook 救不了因 API 错误结束的回合 [S50·T14]。操作者还会在阶段边界重贴目标，或者重新问一遍「你确定我们的目标是这个吗」[S32·T10]。

## 为什么这不是「同时干很多件事」

从轨迹看，操作者的工作只剩三类：

1. **定义**：目标、资源、期限、停止条件，写成文件；
2. **裁决**：回答带推荐项的问题，叫停，换资源；
3. **转发**：把一个 session 的产物（review、调用指南、会话记录）贴给另一个。

轨迹里可以看到执行、审阅、巡检和下一条 prompt 被交给 agent、别的 session 和心跳。系统中的 agent 活跃均值为 3.7；人的注意力投入没有被直接测量，不能由会话活跃均值推算。
