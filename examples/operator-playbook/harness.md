# Harness：每种机制什么时候用、救了什么、在哪里失效

## 1. 派活：subagent 与 teammate

**用法**。操作者只说「agent team 完成」，由 lead 决定落成什么机制：22 个命名的后台 subagent [S32]、12 个 teammate [S28]、一个 cron 且没有 teammate [S63]，或 Codex 的 spawn_agent [S61]。同一句话，在不同的 lead 模型和任务下，落成的机制不同。

**lead 写的派活 prompt 结构基本一致** [S28·T1][S32·T3.1][S65·T4][S50·T1]：角色 → 必读的 brief 或契约 → 负责的文件 → 带 fallback 的编号步骤 → 验收 smoke → 汇报格式和行数上限 → 禁止事项（只读、不许碰某目录、不许 commit）。骨架见 [prompts.md](prompts.md)。

**救了什么**。并行实现互不覆盖 [S32·T3.1]；调研和映射外包出去，lead 留在调度位 [S28·T30]；审计、红队这类只读角色抓到了人不会去读的问题 [S65·T6.1]。

**代价**。teammate 消息每条都会唤醒 lead，重复消息只换来一句 “Nothing new” [S65·T6.13]；长消息会被截断，需要索取全文 [S65·T2.1]；lead 也会违反自己写的规则，由一个 teammate 发现 [S65·T6.2]；子 agent 卡在沙箱上，所以 lead 把沙箱规则写进派活 prompt [S32·T3][S63·T4.1]。

## 2. 心跳：让 session 在人不在时继续

| 机制 | 例子 | 效果 |
|---|---|---|
| 每小时的 cron，prompt 自带命令、路径、验收信号 | [S63·T2][S63·T4.1] | 7 小时人类空档里每小时出一份报告 |
| 目标写进 cron 首句 | [S63·T6] | 从「活着」升级到「有效」，下一次巡检就如实报坏消息 |
| 条件 cron | [S63·T6.4] | 一次授权，夜里执行 |
| 后台计时 + 完成通知唤醒 | [S32·T3.12]–[S32·T9.16] | 约 9.5 小时无人值守的巡检循环 |
| 条件唤醒（服务恢复就醒） | [S32·T9.13] | 外部服务宕机时不空等 |
| ScheduleWakeup 当备用心跳 | [S32·T10][S28·T28] | 主信号是完成通知，wakeup 兜底 |
| Codex automation heartbeat（agent 自建） | [S61·T4.1][S61·T6.1] | 撑过 9 小时夜间；频率从 10 分钟调到 4 小时 |
| `/goal` stop hook | [S65·T6.1][S50·T10] | compaction 之后推动 lead 继续 |

**失效方式**：

- 还没设心跳就早停，空转近 7 小时 [S63·T1]；
- 进程重启会杀掉计时链：第一次有人上弦，第二次无人，静默约 25 小时 [S32·T9 hindsight]；
- goal hook 救不了因 API 错误结束的回合，夜间循环停了约 5 小时 [S50·T14]；
- 心跳太密是噪声 [S61·T4.1–T4.4]，太疏会漏掉两次心跳之间的停摆 [S61·T7]；
- 只查进程活着的监控，会在指标变坏时一直报健康 [S63·T5.2–T5.6]。

没有心跳时，操作者自己就是心跳：「如何了」「继续完成」，一小时发 5 条，有时和另一个 session 同一分钟 [S28·T14–T18]。

## 3. Compaction 与目标

- **手动 compaction 放在换阶段之前**：3 次都紧挨着新阶段指令 [S32]；离开前先 compact 再设 goal [S65·T6][S50·T9]。
- **summary 逐字保留常设规则**、用户选择和资源约束 [S32·T7.8][S28·T21][S50·T9]。在这个操作者的数据里，目标确实会被 harness 带过 compaction；但操作者并不只靠这一点，重要的约束都另外成文。
- **上下文窗口大小改变节奏**：1M 上下文的 lead 连续跑了约 5.5 小时，到 741k token 才手动 compact [S65·T6]；约 200k 的窗口在 13 小时里自动 compact 了 3 次 [S28]。
- **compaction 之后先定位**：ListAgents，重读契约 [S65·T6.1][S28·T21]。

## 4. 人的通道：提问与裁决

- **AskUserQuestion 带推荐项**：操作者几乎总是选推荐项 [S63·T2][S65·T4][S28·T2.1]。例外只有一次：操作者放宽了自己早先定的规则。
- **阻塞批量上抛**：两个阻塞合并成一次提问，人一次答完 [S50·T5]。
- **风险**：挂着的问题会把 lead 卡住 [S28·T2.2]；一个始终没人处理的人工步骤让一整条线停住，请求了 7 次 [S65 hindsight]；在 cron 回合里发问，得赶上人恰好在线 [S63·T6.4]。
- **Codex 的异步提问不阻塞运行**，推荐项有一次被人用自由文本改写，拦下了范围漂移 [S61·T11→T12]。

## 5. Skill、memory 与文件

- 长任务和网页调研这类 runbook 由 skill 提供 [S63·T1][S65·T2]。
- 用到的技能复制进项目，在 AGENTS.md 登记，每次唤醒先读索引 [S61·T3]。
- conventions 写进 memory，留给之后的 session [S65·T6.21]。
- 状态文件、运行台账、编号修订让 compaction、重启和别的 session 都能接上 [S32·T8][S63·T6.4][S65·T5.1]。

## 6. 常见故障

| 故障 | 例子 | 恢复 |
|---|---|---|
| rate limit / API 错误截断回合 | [S63·T1][S28·T14][S50·T13] | 人的「继续」或下一次 cron；截断后常常没人知道 |
| 误把约束当事实（「带宽就是瓶颈」） | [S28·T8.1] | 人追问原因、给出新名字 [S28·T11] |
| 可行性判断过于乐观 | [S28·T1] | 止损换资源 [S28·T24] |
| 过度扩展 | [S50·T1] | 叫停并重述 [S50·T2] |
| 静默停摆 | [S61·T7][S50·T14] | 人问 ETA 或巡检才发现 |
| 推断说过头 | [S32·T3.13] | 外部 review 指出，lead 撤回 |

## 7. 在这位操作者手里，Claude Code 和 Codex 的分工

- **Claude Code** 多用作执行方：agent team、cron、AskUserQuestion、手动 compaction、`/goal`、`/model` 换阶段 [S32][S63][S65]。
- **Codex** 有两种用法：
  - 一是审阅和讲解：读 Claude Code session 的进度，写 review，替操作者写下一条 prompt [S21·T5][S38·T3][S07·T2]；
  - 二是长时间的流水线调度：按阶段拆 subagent、自建 automation 心跳、异步提问、以 AGENTS.md 为索引 [S61]。
- **可观察性不同**：Codex 的 agent 间消息和 compaction summary 在磁盘上是加密的，只能看到对象和时间；Claude Code 的派活 prompt、消息和 summary 都可读。
- **其他 agent CLI 的会话记录**也会被贴进新 session 当起始上下文 [S13·T1][S31·T1]：会话记录本身就是交接物。
- 两晚的对照（推测，任务不同）：Claude Code 的夜间循环在 API 错误后停了 [S50·T14]，第二天晚上 Codex 靠心跳跑过了 9 小时 [S61·T6.1]。差别在唤醒机制，不在模型。
