# 关键时序：6 个代表性 session

挑选标准是覆盖不同类型的工作，不是挑最长的。每个 session 都从结局往回推：找出没有它结局就会不同的几步（关键时序），再用反事实说明为什么关键。领域内容已抽象成角色描述。

---

## S32 · 一个研究项目，由 agent team 推进三天

**目标**：同步进度后先复述项目目的，再找 gap、设计并推进实验，最后做一份交付物。
**结局**：实验跑了两波，一个统计检验被发现失准并更换；交付物的每个数字都有脚本校验。

1. **目标复述探针 → 目标契约成文** [S32·T1→T2]。agent 复述的目的被一句「不对」否定，操作者贴入预先写好的目标陈述。lead 先写 `docs/goal.md`，再做清理。
   *为什么关键*：之后 22 次派活、3 次 compaction summary、两轮交付物 reviewer 都以这份文件为准。没有它，被否定的那版理解就是默认口径。
2. **先红队，后实现** [S32·T3→T3.7]。lead 派出调研、准备环境、红队三个 agent，红队提出的 9 条阻断缺陷全部并入设计后才开工。3 个实现 agent 按文件分工，跨文件的问题由 lead 转发。
   *为什么关键*：没有红队，数据泄漏类缺陷会污染之后每一波实验；没有文件分工，三个实现者会在同一工作树互相覆盖。
3. **跨 session 审阅回灌** [S32·T4][S32·T7]。另外两个 session（其中一个是另一个 harness）写了只读 review，操作者把路径贴回来：「你觉得这部分的 review 正确吗？」lead 逐条对照代码核实，全部接受，并撤回自己一处推断过头的说法。
   *为什么关键*：当时测试全绿，review 抓到的是单测看不见的契约级缺陷。
4. **重启后上弦** [S32·T9]。进程重启 1 分钟后，操作者发了一句「继续完整迭代好。」lead 接着跑「后台计时 → 完成通知唤醒 → 巡检 → 写状态文件 → 再设计时」的循环，无人值守约 9.5 小时。
   *为什么关键*：第二次重启时没人上弦，session 静默了约 25 小时。同一个 session 里的这组自然对照说明，计时循环扛不过重启。
5. **负对照当校准器** [S32·T9.14]。一条不该赢的对照臂也通过了检验。lead 作废同类结论，派统计审计从原始数据重建，改用更严格的预注册检验。
   *为什么关键*：没有这条对照臂，一个噪声结果会被当成正结果。
6. **数字断言 + fresh-eyes reviewer** [S32·T11.3][S32·T11.5]。交付物由脚本生成，每次构建都断言全部数字；两轮独立 reviewer 抓出三处归因错误。
   *为什么关键*：没有它们，三处归因错误会进入交付物。

**Hindsight**：同一项目同期至少还有 5 个 session，彼此之间唯一的总线是仓库里的 goal.md、状态文件和 review 文件。
**词表**：goal read-back · goal contract · adversarial member · file ownership · review relay · re-arm · negative control · number-checked build

## S63 · 一个集群上的训练作业，由 cron 看守

**目标**：看一行贴来的运行状态，判断要不要重训；之后确保训练有效。
**结局**：旧 run 被确认发散后停掉；换一种方法的切换写进条件 cron，在夜里执行。

1. **看门狗之前的早停** [S63·T1]。第一轮先撞上一次故障，又撞上 rate limit，还没设 cron 就停了。session 静默近 7 小时。
   *为什么关键*：假如第一步先建 cron，下一个整点就能恢复，发散的判断能提前好几个小时。
2. **先设看门狗，再一键裁决** [S63·T2]。「如何了」之后，agent 先建每小时 cron，再诊断，再用 AskUserQuestion 给出带推荐项的选项；操作者一键选「停训、改 recipe 重起」。
   *为什么关键*：停掉跑了几个小时的 GPU 作业不可逆。提问让人保留决定权，代价只是点一下。
3. **目标写进心跳** [S63·T6]。操作者说「反正确保训练好」，cron 的第一句变成 “Goal: ensure training is GOOD, not just alive.”
   *为什么关键*：之前的 cron 只查进程是否活着，一直报健康；改完后的第一次巡检就如实说「只减速、没拆弹」。
4. **条件 cron** [S63·T6.4]。第二次一键授权后，agent 把「某个 checkpoint 写完就停旧 run、起新 run、记账、验证」写进 cron。
   *为什么关键*：条件要 8–10 小时后才满足。没有它，GPU 要么空转，要么继续跑一个已知失败的 run。

**Hindsight**：人的 prompt 一共不到 200 字，目标几乎全靠 cron prompt 和状态文件承载。第二次提问恰好发生在操作者在线的时候；若不在线，cron 回合会停在提问上。
**词表**：watchdog first · question gate · goal injection · conditional cron · pre-registration

## S28 · 部署并评测一批候选模型

**目标**：把几个候选模型部署起来，和基线对比；后来扩大到一张公开榜单上的全部候选。
**结局**：25 个候选里 24 个在同一套评测上出了结果，并按实现机制归类；本地和远端的权重全部清理。

1. **contract-first** [S28·T1]。lead 判断所有候选共享同一种接口，于是每个模型只写一个薄适配层就能接进现成评测；部署的 agent 不做评测。
   *为什么关键*：否则每个候选各写一套评测，结果之间不可比。
2. **止损换资源** [S28·T23→T26]。本地跑了一夜只多测完 1 个。操作者拒绝一个 tool call、打断，一句「算了，本地不要测试了」，3 分钟后贴出远端 4 卡服务器的访问方式和「agent team 完成」。
   *为什么关键*：同一类模型在本地首个请求要几十分钟，在远端是秒级。不换，结局是 5 个候选只测完 2 个。
3. **外部清单当 scope + 卡不能停** [S28·T27→T28]。一张榜单截图加一句「把这些都测试一下」「卡不能停」。
   *为什么关键*：最终最好的几个都不在最初的候选里。
4. **先分类再泛化** [S28·T28.1→T30]。调研 agent 发现多数条目只是通用底座上的推理框架；lead 让一个 teammate 只写两类通用适配层。
   *为什么关键*：这个 teammate 约 3 小时接入 13 个模型，包括最终最好的几个。
5. **只要结果，定停止条件** [S28·T32→T38]。「给我看看结果就行」「测这两个就行」「算了，暂停」。
   *为什么关键*：最后一个模型卡在依赖上两个小时，不收尾会一直追下去。

**Hindsight**：前 5 小时双方都在优化下载，真正的瓶颈是本地算力。暂停和清空 GPU 几乎与另一个 session 的「那边 ok 了，你直接跑」同时发生（推测是在让卡）。
**词表**：one-phrase delegation · role split · cut-and-switch · utilization rule · stop rule · result-only closure · human heartbeat

## S65 · 在一个 goal 下做调研和新算法

**目标**：调研一个领域的已发表工作，提出一个与它们都不重合的新方法，然后把实验跑起来。
**结局**（快照，session 仍在运行）：综述、新提案和实验框架都已完成，比较性实验还没开始。

1. **「不撞车」约束 → 对抗式 fan-out** [S65·T1→T2]。8 个分主题调研 teammate 加 1 个 novelty-checker，后者的任务是 “try HARD to show … NOT novel”。
   *为什么关键*：没有这条约束，产出只是一份描述性综述；有了它，每个组件都做了重合检查。
2. **资源指针 → 计划契约** [S65·T4]。一句话给出资源（另一个 session 写的调用文档）、并发数和「agent team 完成」。lead 写实验计划当契约，派 5 个 teammate 按文件分工。
   *为什么关键*：约 1.5 小时后，基础设施和 60 并发实测都已完成，彼此没有冲突。
3. **交出自己的计划，允许发散** [S65·T5]。「发散，不要固定于我的代码和思路」。之后的冲突都写成编号修订。
   *为什么关键*：比较对象从「新方法对基线」扩成同预算下的多臂比较。
4. **离开前 compaction + goal，再做只读审计** [S65·T6→T6.6]。goal hook 第一次推动时，lead 派了一个只读审计员，找出 3 个会系统性偏向新方法的公平性缺陷。
   *为什么关键*：没有这次审计，同预算比较会偏向新方法，结论经不起推敲。
5. **smoke 暴露处理没生效 → 预注册修订** [S65·T6.16]。smoke 显示被比较的处理几乎没有生效。lead 称之为 “the decisive issue … before the spend”，修订写明动机来自 smoke 的测量，而不是比较结果。
   *为什么关键*：否则全量运行测到的是被稀释的效应。

**Hindsight**：唯一需要人做的一步（在一个数据集页面点同意）被请求了 7 次，一次都没被满足。goal 在其中的作用是推测：teammate 的消息本来也会唤醒 lead。
**词表**：adversarial member · goal contract · numbered amendment · smoke before spend · pre-registration · time horizon · resource handoff

## S61 · Codex 里的一条数据流水线

**目标**：按 agent 自己的诊断改造一条训练数据流水线，放量生产，再对齐下游模型的需要。
**结局**：数据按新的样本单位产出；下游适配问题在训练前被发现；最后让出服务给另一个 session。

1. **先诊断，再授权** [S61·T1→T2]。第一轮只读不改；「参考你的分析，完整修改一下」把诊断变成授权，同时给出推送检查点和 smoke 门。
   *为什么关键*：跳过诊断直接放量，会在错误的样本单位上批量产出错标数据。
2. **技能入库** [S61·T3]。「防止到时候我一个一个要说一次」：用到的技能复制进项目，在 AGENTS.md 登记。
   *为什么关键*：夜里的唤醒隔着 3 次 compaction，靠这份索引拿到规则。
3. **放量 + 运营契约 + 调整心跳频率** [S61·T4→T5]。agent 自建 10 分钟一次的心跳；操作者一条消息定下运营约定、磁盘护栏、「4h 一次」。
   *为什么关键*：10 分钟一次的唤醒在夜里会空转几十次；约束只在对话里的话，扛不过后面的 compaction。
4. **按下游目标重新锚定** [S61·T9]。「重点是打标完成之后可以正确处理好数据集的格式」→ 新的数据契约、新子代理、验收指标改为直接衡量下游质量。
   *为什么关键*：否则产出会继续按最初的方案优化，和真正要训练的场景错位。
5. **价值闸门** [S61·T11→T12]。为了「卡满载」，agent 提议用重复请求压测；操作者回「我的意思是我们的任务一直跑就行」。
   *为什么关键*：这是本 session 唯一一次被拦下的范围漂移，拦下它靠的是提问，不是审阅。
6. **写调用指南，让出资源** [S61·T13→T18]。36 分钟后，另一个 session 引用这份指南开了 60 并发 [S65·T4]。
   *为什么关键*：否则两个 session 会争用同一个服务。

**Hindsight**：4 小时的巡检节奏也有代价：一次停摆夹在两次心跳之间，是操作者问了一句 ETA 才发现的 [S61·T7]。数据、规则、代码都没有人工阅读的痕迹，替代它们的是 agent 侧的门。
**词表**：smoke before spend · skill vendoring · cadence tuning · goal contract · value gate · resource handoff · model routing

## S50 · 一个 skill 加一个 benchmark，夜里的循环死了

**目标**：续做一个 skill，建 benchmark 做对比，再让它按 benchmark 自己迭代一夜。
**结局**：benchmark 完成；夜里的迭代循环在一串 API 错误后停了约 5 小时，第二天换了新 session 重来。

1. **借来的考题 + 对照矩阵** [S50·T1]。考题用现成的原文，一字不改；操作者只加被测对象和主/子模型组合。
   *为什么关键*：原文自带收束和篇幅规则，后来 skill 的阶段设计和评审维度都对应这些规则。
2. **叫停并重述对比轴** [S50·T2]。「先不管啊。我们对比的是…」「我觉得你有点 overthinking 了？」lead 3 分钟内停掉 6 个子代理。
   *为什么关键*：否则 6 个子代理会把 session 变成亲自调研一个技术主题。
3. **一行加一条对照臂** [S50·T4→T5]。每行加一个外部 harness 并给出主/子模型；两个阻塞合成一次提问，人答「升级 / 跳过」。
   *为什么关键*：有了跨家族的臂，结论才站得住。
4. **讲给我听 + 外部参照** [S50·T7→T8]。操作者要 agent 讲结论；再拿一份外部同题文档来同尺盲评。
   *为什么关键*：这是操作者唯一一次消费结果，它暴露的失分点正好成为夜间迭代的两个方向。
5. **先 compaction 再立目标，用一个名字启动循环** [S50·T9→T10]。`/goal` 里点名一个开源的 autoresearch 循环，lead 把它展开成完整的迭代协议。
   *为什么关键*：一个名字代替了一整段流程描述。
6. **巡检 → 打断 → 换 session** [S50·T14]。夜里 API 错误之后没有任何机制唤醒 session；早上一句「继续完成呢？」之后，操作者打断，6 分钟后开新 session，第一句是「你先说我们的目标是什么，现在完成到哪一步了」[S52·T1]。
   *为什么关键*：`/goal` 的 stop hook 救不了因 API 错误结束的回合。第二天晚上 S61 用心跳撑过了 9 小时，差别在唤醒机制，不在目标声明（推测：两晚的任务也不同）。

**词表**：brake and restate · question gate · explain-back · time horizon · watchdog first（反例） · goal read-back
